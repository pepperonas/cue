# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`cue` — a multi-tenant prompt-/todo-queue web app for managing Claude-Code-CLI prompts.
Capture prompts, group by project, work them through a status workflow (Queued →
Running → Done, plus Failed/Archived), and copy them into the CLI with one click.
Deployed at `https://cue.celox.io` behind a reverse proxy. Repo: `pepperonas/cue` (private).

Hard constraints: **multi-tenant** — sign in with **Google OAuth**, each user owns their own
projects/prompts (`User` table + `user_id` FK on every owned row), access gated by an
email/domain allowlist. MD3 Expressive design with real spring motion, footer
`© 2026 Martin Pfeffer | celox.io` on every page.

```bash

pnpm build                                 # tsc -b && vite build -> dist/
pnpm typecheck
pnpm vitest run                            # frontend unit tests (src/lib only)

# All suites + badge refresh (from the repo root; root package.json)
npm test                                   # backend + runner + frontend, then posttest
npm run update-badges                      # refresh README LOC/test badges (idempotent)

# Full app (prod): one container serves API + built frontend
docker compose up -d --build               # listens on 127.0.0.1:8791
# Auth needs GOOGLE_CLIENT_ID/SECRET + an allowlist in .env (see .env.example).
```

After backend or frontend changes, run `uv run pytest` and `pnpm build` before committing
(or `npm test` from the root to run all three suites — it also refreshes the README badges
via the `posttest` hook).

**Testing conventions:** three suites — `backend/tests/` (pytest, black-box over the HTTP
API with a real tmp SQLite; shared fixtures/helpers in `conftest.py`: `client`, `auth()`,
`make_user()`, `RUNNER_HDR`/`CAPTURE_HDR`), `cue-runner/tests/` (pytest + pytest-asyncio,

(Vitest, only pure lib modules — UI components are deliberately untested). Test behavior,
not implementation; external deps (Google OAuth via monkeypatched `_post_form`/`_get_json`,
subprocesses, browser APIs) are mocked; everything runs offline and deterministically.
Coverage: backend 98 %, runner 91 % (`--cov=app` / `--cov=cue_runner`); remaining gaps are
defensive except-branches, `__main__.py` and a few executor cancel branches. `scripts/update-badges.mjs` maintains 11 DYNAMIC badges between `<!-- badges:dynamic -->` markers in README.md (marker block must exist): version (single source = `backend/app/main.py` — the badge syncs automatically, only bump main.py), tests total + per suite (`pytest --collect-only` / `vitest list`, never grep `it()`), backend+runner coverage (`pytest --cov` TOTAL, threshold colors), LOC total + Python/TS split, API-endpoint count (route decorators). Runs on every `npm test` via posttest; idempotent.

## Architecture

**One process, one port.** FastAPI mounts the JSON API as a sub-app at `/api` and serves
the built frontend (`STATIC_DIR`, default `static/`) as a SPA for all other paths, with an
`index.html` fallback so client-side state survives hard reloads. In dev the two run
separately and Vite proxies `/api` to `:8000`.

**Backend (`backend/app/`)**
- `main.py` — app assembly, lifespan (`init_db`), security-header + CSP middleware, `/api` mount, SPA static serving (with path-traversal guard).
- `config.py` — env-driven `Settings` (cached). `validate()` fails fast (needs `SECRET_KEY` + `GOOGLE_CLIENT_ID`/`SECRET`) unless `CUE_DEV=1`. `is_email_allowed()` enforces the allowlist (empty lists = closed in prod, open in dev). `google_redirect_uri` derives from `ALLOWED_ORIGIN`.
- `db.py` — SQLite engine; a `connect` event sets `WAL`, `foreign_keys=ON`, `busy_timeout`. `init_db` runs `_migrate()` — idempotent `ALTER TABLE` (PRAGMA-guarded) for additive columns (`bookmarked`, `bookmark_order`, and `user_id` on `prompt`/`project`), since `create_all` only adds missing *tables*, never columns (no Alembic).
- `models.py` — `User` + `Project` + `Prompt` (SQLModel tables). `PromptStatus` enum. Every owned row has a `user_id` FK to `user`; `Prompt.bookmarked`/`bookmark_order` back the bookmarks section; `Prompt.tested` flags whether a **done** prompt's feature was tested. Project name uniqueness is **per user**, not global.
- `schemas.py` — Pydantic request/response models (kept separate from table models). `MeResponse` carries `UserRead`.
- `security.py` — itsdangerous signers: session tokens (payload carries `uid` + the CSRF secret), CSRF double-submit check, and short-lived OAuth-`state` tokens (`issue_oauth_state`/`oauth_state_valid`) to guard the Google redirect. No passwords.
- `deps.py` — `current_session` (401 guard), `current_user_id` (extracts `uid` from the session — inject this into every data router to scope by tenant), `require_csrf` (403 guard + Origin check), `get_client_ip`.
- `routers/` — `auth` (Google OAuth), `projects`, `prompts`, `attachments`, `runs`, `importexport`. **Every data query is filtered by `user_id`; ownership is re-checked on get/update/delete (404 if not owned).**
- **Prompt capture** (`models.CaptureSession/CapturedPrompt`, `routers/capture.py`): every prompt typed in the Claude Code CLI is logged into cue via a `UserPromptSubmit` hook → spool → the cue-runner's forwarder → `POST /api/capture` (Bearer `CAPTURE_TOKEN`, attributed to `OWNER_EMAIL`'s user). Items carry `{session_id, cwd, git_root, prompt, seq}`; the project is derived under `CAPTURE_BASE` (`Settings.capture_project_name`, auto-creates the project): preferred from the hook-reported **git root** relative to the base with `_`-prefixed grouping folders skipped (`_customers/celox/website` → project `celox/website`; an all-underscore root keeps its own name), fallback = first non-`_` `cwd` segment (old hook / no repo / root outside base; `_customers/celox` → `celox`), grouped into a `CaptureSession` per Claude `session_id`, deduped on `(session, seq)`. Owner-facing history: `GET /api/sessions(/{id})` (session detail lists prompts newest-first, `seq` desc), `POST /api/sessions/{id}/prompts/{cp}/promote` (captured → real queued prompt), `DELETE /api/sessions/{id}`. **Multi-tenant:** `/api/capture` resolves the Bearer token to a user — the env `CAPTURE_TOKEN` → `OWNER_EMAIL`, or a per-user `User.capture_token` → that user (with `User.project_base` for derivation). Sessions endpoints + the **Verlauf** tab are per-user (`current_user_id`, not owner-gated); `Settings → Prompt-Capture` lets any user set their base + (re)generate their token. The runner sets `CUE_NO_CAPTURE=1` on its own `claude` execs; its forwarder throttles retry errors. Hook lives in `~/.claude/settings.json` (`python3 …/cue-runner/hooks/capture_hook.py`); runner needs `CAPTURE_TOKEN` in `cue-runner/.env`. All phases done.
- **Send a prompt into a live CLI session** (`models.CliDelivery`, `routers/capture.py`, reverse of capture): the capture hook additionally records each session's terminal context (`ITERM_SESSION_ID`, `TMUX`/`TMUX_PANE` → `CaptureSession.term_program/iterm_session_id/tmux_pane/tmux_socket`, refreshed on every ingest); a session is `deliverable` when a transport is known. Owner-only `POST /api/sessions/{id}/send {text, submit}` enqueues a `CliDelivery` (`queued`); the runner claims it atomically via `GET /api/cli/claim` (guarded by `RUNNER_TOKEN`, mark `sending`), performs it, and reports via `POST /api/cli/{id}/result`; the frontend polls `GET /api/cli/{id}`. **Owner-only** (`require_owner`) because it drives a terminal on the runner's machine, exactly like runs. Runner transport = `cue_runner/deliver.py`: **iTerm2** via `osascript` (AppleScript `write text`, GUID from `ITERM_SESSION_ID`) and **tmux** via `paste-buffer`, both using **bracketed paste** (ESC[200~…ESC[201~) so multi-line prompts land as literal input; then an optional Enter to submit. All ids validated + argv-only (no shell/AppleScript injection). Runner delivery loop polls `GET /api/cli/claim` every `DELIVER_INTERVAL` (1.5 s; `CUE_DELIVER=0` disables). **iTerm2 needs a one-time TCC Automation grant** for the runner's process. Frontend: `SendToSessionDialog` + "An CLI senden" in `DetailSheet` (gated on `canRun`).
- **Run engine** (`models.Run/RunStep/RunLog`, `routers/runs.py`): execute saved prompts through the Claude Code CLI on a Mac **runner** that polls cue. A `Run` is `single` (one step) or `chain` (ordered steps in one Claude session); `RunStep` snapshots the prompt text (reproducible). **User endpoints** (`POST/GET /runs`, `GET /runs/{id}?after_seq=`, `POST /runs/{id}/cancel`, `GET /runs/config`) use cookie auth and are **owner-only** (`require_owner` → `OWNER_EMAIL`; the run executes code on the runner's machine, so it must not be open to other allowlisted users). **Runner endpoints** (`POST /runs/claim`, `/runs/{id}/heartbeat|log`, `/runs/{id}/steps/{idx}/result`, `/runs/{id}/result`) are guarded only by `RUNNER_TOKEN` (`require_runner`, Bearer). Claim is **atomic** (single `UPDATE ... WHERE status='queued' ... RETURNING id`). `project_path` is whitelisted via `Settings.is_path_allowed()` against `ALLOWED_PROJECT_BASES` (string-only on the VPS; the runner re-validates). Chains thread one Claude session; the runner pre-assigns it via `--session-id <uuid>` then `--resume` (CLI v2.1.195 has **no `--cwd`** → set subprocess cwd; **no `--max-turns`** → rely on per-step timeout + `--permission-mode`). Cancel sets `cancel_requested` (running) or `canceled` (queued); the runner learns it from the heartbeat response. The Mac daemon lives in **`cue-runner/`** (own venv/pyproject, PM2-able): asyncio claim-loop, step exec via `create_subprocess_exec` (sets `cwd`, `stdin=DEVNULL` to skip the CLI's stdin wait, parses `stream-json`), heartbeat (also picks up cancel), SIGTERM→SIGKILL cancel, per-step timeout; its own `ALLOWED_BASES` re-validation. `cue-runner/` is **not** deployed to the VPS — it runs on the Mac where `claude` is authenticated. **Frontend** (`RunsView`, `RunDialog`, `state/queries` `useRunConfig/useRuns/useRun/useCreateRun/useCancelRun`): the **Runs** tab + the prompt "Ausführen" action + select-bar "Ausführen" (1 prompt = single, ≥2 = chain) are gated on `useRunConfig` succeeding (owner-only; a 403 hides them, `canRun`). `RunDialog` picks a project base from the whitelist + optional subfolder, model/permission-mode/allowed-tools/bare/skip-permissions/stop-on-error — the last-used settings persist in `localStorage` `cue-run-prefs` and are restored on open (validated against the config whitelists; the **subfolder** deliberately always starts empty); `RunsView` polls (`refetchInterval`) for a live status + log tail, copyable session id, cost, cancel, and re-run. **Hardening (P4):** `runs.reap_stale()` fails runs stuck in claiming/running whose `last_heartbeat` is older than `RUN_STALE_TIMEOUT` (also cleans up runs left in-flight across a backend restart); a `_run_reaper_loop` in the lifespan runs it at startup and every 60 s. The runner heart-beats independently of step progress, so long steps aren't falsely reaped. (P1 backend + P2 runner + P3 frontend + P4 hardening done; P5 = e2e/docs/version + live runner.)
- **Snippet library (Inspector-Rust roundtrip workbench)** (`models.Snippet/SnippetGroup`, `routers/snippets.py`, format contract in **`app/ir_format.py`** — pure parse/build, no DB/FastAPI, tested incl. a golden roundtrip against `tests/fixtures/ir-backup-snippets.json`): import an IR backup JSON → edit/structure in cue (Snippets tab) → export an IR backup that IR's "Settings → Backup & restore → Import" reads. **Write-side invariants:** `version` MUST be 2, timestamps are unix MILLIS, `abbreviation` is IR's merge key (verbatim, trim only), groups travel by NAME (`snippet_categories` carries EMPTY groups + order), `category` is three-valued (`"name"` assign · `""` explicitly ungroup · `null` = leave IR untouched) — cue exports `""` for ungrouped, NEVER `null`; history/notes/totp_entries/settings stay empty. Read side is tolerant (full envelope / snippets-only / legacy `[{abbreviation,body}]` → ungrouped; encrypted backups rejected with a clear message; per-row errors collected, never fatal). Import merges: upsert per `(user_id, abbreviation)` (unique per tenant, enforced in the router like `Project.name`), group get-or-create by name, `category: null` never clobbers a cue-side move. `SnippetGroup` exists only so empty groups + order persist; rename back-fills the denormalized `snippet.group_name` in one txn; NO index on `SnippetGroup.name` (SQLModel's auto name would collide with `snippet.group_name`'s `ix_snippet_group_name`). Export supports `?groups=a,b`. Frontend: `SnippetsView` (dnd-kit with two id namespaces — numeric snippet ids + `sec:<name>` for group headers/droppables), `SnippetEditor` (live duplicate check via `lib/snippets.ts:abbreviationTaken`), grouping helper `lib/snippets.ts:groupSnippets` (vitest-tested; orphaned group names still render). **Versioning (0.17.0, roundtrip since 0.19.0):** `Snippet.version` starts at 1 and bumps ONLY on content changes (abbreviation/title/body); group moves, reorder, bulk-move and no-op saves don't bump. Since 0.19.0 the version IS in the envelope as an ADDITIVE per-snippet field (older IR ignores unknown keys); shared cue<->IR merge rule on import: content differs -> `max(incoming, local+1)`, identical -> `max(incoming, local)`, missing/0 -> 1 — re-importing cue's own export is a no-op and both sides converge. UX (0.15.1): search field over abbreviation/title/body (`lib/snippets.ts:filterSnippets`, hides empty groups while searching), visible select mode with row checkboxes + per-group select-all (Cmd/Ctrl+click still toggles), snippets sort ALPHABETICALLY by abbreviation within each group (0.21.1, matching IR — `groupSnippets` ignores `sort_order`, row drag/reorder removed on purpose; group moves go through the editor's group field or bulk-move; group HEADERS stay drag-sortable, disabled while searching/selecting), copy-body button per row. Group create/rename go through `InputDialog` (inline duplicate validation); snippet deletes (editor + bulk) confirm via `Confirm` with a merge-semantics reminder. The UI permanently hints that IR imports MERGE: cue-side deletions/renames don't delete in IR.
- **Automatic IR sync (0.21.0)** (`routers/sync.py`, `models.SnippetTombstone`, per-user `User.snippet_sync_token`/`sync_ungrouped`/`snippet_sync_last`, `SnippetGroup.synced`): IR polls `GET /api/sync/snippets` (Bearer sync token) and pushes back via POST — cue never reaches out. **Scope is managed ONLY in cue** (☁️ `ToggleIconButton` in each group header + on „Ohne Gruppe"; token in Settings → Snippet-Sync). Sync merge (deliberately different from the manual-import merge): incoming.version > local → adopt content; equal+identical → no-op; equal+different → cue wins; lower → keep local. **Grouping is NOT version-gated — cue is the organizational master** (IR adopts cue's grouping on tie, cue ignores incoming categories for existing snippets). **Tombstones** (`snippet_tombstone`, 90-d TTL, pruned in the pull): every delete/bulk-delete/abbreviation-rename records `{abbreviation, version}` (helpers `record_tombstone`/`resurrect_floor` in `routers/snippets.py`); a tombstone deletes the peer copy only if `peer.version <= tombstone.version`, and (re)creation over a tombstone starts at `tombstone.version + 1` (`resurrect_floor` in create/update/import/sync) — otherwise the next cycle would re-delete it. `record_tombstone` refreshes `deleted_at` only when the version INCREASES (peers echo tombstones back every cycle; refreshing unconditionally would keep them alive past the TTL). The IR counterpart lives in inspector-rust `core/rust-lib/src/sync.rs` (worker thread, 60 s + wake after every snippet mutation, `snippets-synced` Tauri event → UI reload); wire format = `SyncSnippetItem`/`SyncTombstoneItem` field names, do not rename them casually.
- **Central tag vocabulary (0.25.0)** (`models.Tag`/`PromptTag`, `app/tags/`, `routers/tags.py`): tags became a first-class entity instead of comma strings. `tag` holds identity, display spelling, `name_ci` (the lower-cased **uniqueness key per tenant** — that is what makes `Feature` and `feature` one tag), `source` (`user`/`system`) and `last_used_at`; `prompt_tag` is the **source of truth** for assignments. **`Prompt.tags` survives as a denormalized comma cache** with exactly ONE writer (`TagService`) — same pattern as `Snippet.group_name`, which keeps list/search/export/clients unchanged; `rebuild_cache()` is the repair hatch and is covered by a test. Layering: router (HTTP) → `service.py` (normalize, get-or-create, rename/merge, delete/replace, backfill) → `repository.py` (SQL + usage aggregation via one grouped join, no stored counter that could drift). **Rename onto an existing tag MERGES** (assignments move, duplicates drop, the loser row disappears); **delete** optionally re-points assignments to another tag (`?replace_with=`). **Every** prompt write path (create/update/duplicate/merge) goes through `TagService.set_for_prompt`; stats read the tag tables instead of re-parsing strings. **Migration:** `db._migrate_tags()` runs `backfill_from_strings()` per tenant on startup — idempotent (prompts that already have links are skipped), marks migrated tags `source=system` and backdates `created_at` to the prompt that introduced them (14 tags / 165 assignments in production). Frontend: `TagsView` (Tags tab: search, sort, usage, provenance, rename, delete-with-impact-preview), `lib/tags.ts:rankSuggestions` (exact > prefix > word-start > substring, then usage, then recency — unit tested) fed by `mergeSuggestionPool(vocabulary, DEV_TAGS)`, so the ~1.100-entry catalogue stays a static file and only materializes as a row once used. **Gotcha:** deleting a prompt now needs `_detach_references()` + an explicit `session.flush()` — without an ORM relationship SQLAlchemy has no delete ordering, and `foreign_keys=ON` rejected the parent DELETE (that was a live 500 for optimized prompts).
- **Prompt optimization (0.23.0)** (`app/optimization/`, `routers/optimize.py`, executor in `cue-runner/cue_runner/optimize/`): rewrite a saved prompt with the **Claude Code CLI**. Layering is strict — `routers/optimize.py` (HTTP only) → `service.PromptOptimizationService` (rules: versioning, batches, applying results, logging) → `repository.OptimizationRepository` (SQL only) → `providers.py` (strategy registry) → `meta_prompt.py` (the ONE definition of how a prompt is improved, versioned via `META_PROMPT_VERSION`). **The CLI does NOT run on the server** — the VPS container has no `claude` and no auth, so optimization reuses the run engine's shape: the backend queues a `PromptOptimization`, the **Mac runner** claims it (`POST /api/optimizations/claim`, Bearer `RUNNER_TOKEN`, atomic single-UPDATE like `runs.claim`), executes `claude -p <prompt> --output-format json` and reports back (`/result`). User endpoints are **owner-only** (`require_owner`) for the same reason runs are. **The original is never overwritten:** `Prompt.body` stays untouched, the result lands in `Prompt.optimized_body` (+ `optimized`, `optimized_at`, `optimization_model`, `optimization_version`), and every attempt is a `prompt_optimization` row (v1, v2, … with `original_text`/`previous_text` snapshots + exit code, duration, cost, tokens) — that table IS the history. Re-optimizing sends BOTH the original and the last result (`build_meta_prompt(original, previous)`). **Batches** (`OptimizationBatch`) queue every eligible prompt; the runner's `_optimize_loop` works them off **strictly one at a time** (own poll loop, never parallel), ineligible prompts are skipped not fatal, a cancel flags the batch (claim skips it, queued jobs are canceled, a running one finishes). `service.reap_stale()` runs on the same 60 s tick as the run reaper. **Security:** the prompt travels as its own argv element (`create_subprocess_exec`, no shell anywhere), runner secrets are stripped from the child env, models that look like flags are dropped, size cap + timeout + stdout cap are enforced on both sides. Config lives ONLY in `Settings` (`OPTIMIZE_ENABLED/PROVIDER/MODEL/TIMEOUT/MAX_CHARS/MAX_RETRIES/STALE_GRACE`). Adding an OpenAI/Gemini/Ollama optimizer = one `ProviderSpec` here + one `OptimizerProvider` in the runner; nothing else changes.
- **Activity log + statistics (0.22.0)** (`models.PromptEvent`, `app/events.py`, `app/stats.py`, `routers/stats.py`): the **Statistiken** tab is fed by an append-only `prompt_event` log — one row per created/updated/status_changed/deleted prompt, written ONLY through `events.record()` (called from `prompts.py`, `runs.py`, `importexport.py`). It carries `user_id`, `prompt_id`, a `project_id`/`status`/`body_len` snapshot and `at`, and deliberately has **no FK on `prompt`** (the log must outlive the row — that's the whole point of the `deleted` event, and `foreign_keys=ON` would block the delete). `db._seed_prompt_events()` back-fills a plausible history from `created_at`/`ran_at`/`updated_at` on first migration (approximate; pre-migration deletions are unrecoverable); `events.prune()` drops rows past `RETENTION_DAYS` (730) from the daily GC loop in the lifespan. **`app/stats.py` is the single aggregation service** — FastAPI-free, so it is unit-testable and reusable for future exports/digests: `resolve_range()` turns a preset (`today/yesterday/7d/30d/90d/year/last_year/all/custom`) into a `TimeRange` (plus the equally long previous window for every delta), `pick_granularity()` coarsens hour→day→week→month with the span, `bucket_starts()` produces gap-free axes, and one `_*_section()` per domain (prompts/projects/tags/activity/ai) builds the payload. **Timezone:** the client sends its IANA zone (`?tz=Europe/Berlin`) and ALL bucketing happens in it — aggregating in UTC would file late-evening work under the wrong day and shift the "busiest hour". **Point-in-time facts** (status distribution, backlog, lengths) read live `prompt` rows, **time-sliced facts** read the event log. Results are cached per `(user, version, range, tz)` with a 120 s TTL; `events.record()` calls `stats.invalidate(uid)`, so a write is reflected immediately without polling. Always normalise timestamps through `_local()` before subtracting — rows from SQLite come back naive while freshly written ones are still aware, and mixing them raises (regression-tested).
- **Attachments (screenshots)**: `Attachment` table (`user_id`, nullable `prompt_id`, stored `filename`, `original_name`, `content_type`, `size`). Files live in `ATTACHMENTS_DIR` (set to `/data/attachments` in prod so they persist on the volume). `routers/attachments.py`: `POST /attachments` (multipart, image-only, ≤`MAX_ATTACHMENT_BYTES`) returns `{id,url,name,...}` with `prompt_id=null` (pending); `GET /attachments/{id}` serves the file (ownership-checked, not static); `DELETE /attachments/{id}`. Prompts associate them via `attachment_ids` on create/update (`_attach`), and `PromptRead.attachments` is populated by `_reads()`/`_read()` in `prompts.py` (batch-loaded). `delete_prompt` purges files; `merge` reassigns source screenshots to the merged prompt when originals are deleted. **Auto-expiry**: `attachments.purge_expired()` deletes attachments older than `ATTACHMENT_TTL_DAYS` (30); a daily background task (`_attachment_gc_loop` in `main.py`'s lifespan) runs it. The Composer shows a dismissible inline notice about the 30-day deletion (`localStorage` `cue-hide-attach-notice`).

**Auth (Google OAuth, Authorization Code flow)** — `routers/auth.py`:
- `GET /auth/google/login` → signs a `state`, sets it as a `SameSite=Lax` cookie (must survive Google's top-level redirect back), 302s to Google's consent screen.
- `GET /auth/google/callback` → validates `state` vs the cookie, exchanges the `code` for an access token (`oauth2.googleapis.com/token`, with the client secret), fetches the profile (`openidconnect.googleapis.com/v1/userinfo`). Both calls are stdlib `urllib` over TLS, so no id-token signature check and **no extra runtime dependency**. Rejects unverified emails and anyone failing the allowlist. Upserts the `User` by `google_sub`, issues the session, and — for `OWNER_EMAIL`'s first login — claims all `user_id IS NULL` rows (the original single-user data).
- `GET /auth/me` → `{authenticated, csrf_token, user}`. `POST /auth/logout` clears cookies.
- The session cookie stays `SameSite=Strict`; only the transient `state` cookie is `Lax`. Session salt is `v2` (carries `uid`), so old single-user sessions are invalidated.

**Frontend (`frontend/src/`)**
- `lib/color.ts` — Material-You tonal-palette generator from a seed hex (HSL-tone approximation, no heavy dep); `buildSchemes` → light/dark role tokens applied as `--md-*` CSS vars.
- `lib/motion.ts` — MD3 spring presets; all motion respects `prefers-reduced-motion`.
- `lib/api.ts` — typed fetch client; reads `cue_csrf` cookie and sends `X-CSRF-Token` on mutations.
- `lib/markdown.ts` — tiny escape-first Markdown renderer for previews (no DOMPurify needed: HTML is escaped before the markdown subset is applied).
- `lib/tags.ts` — curated English software-dev tag list (`DEV_TAGS`, ~1100 categorized entries) backing the tag autocomplete. Invariants are pinned by unit tests: no case-insensitive duplicates, lowercase single-token (hyphens, no spaces), American spelling only (a test rejects -isation/colour/behaviour/…) — extend the list accordingly.
- `components/TagInput.tsx` — comma-separated tag field with type-ahead. Completion targets the token after the last comma; `↑/↓` navigate, `Enter`/`Tab`/click commit, `Esc` closes. The Composer feeds it a pool of tags already used across prompts (via `usePrompts`) first, then `DEV_TAGS`, deduped case-insensitively. The suggestion list **flips upward** (`.tag-suggest.up`, decided from the input's viewport rect in `recalcDirection`) when there isn't room below — the tag field is the dialog's last field, so a downward menu would otherwise cover the "Anlegen"/"Abbrechen" action buttons. (A sticky action footer was tried and rejected: pinning it to the sheet bottom made it overlap the focused tag input.) **Tags are deduplicated case-insensitively per prompt**: `commit()` won't add a tag the prompt already has, and `normalizeTags`/`dedupeTags` (`lib/tags.ts`) dedup on Composer save + on `PromptCard` render, so a tag can never appear twice on one prompt (kept as a shared helper, first spelling wins).
- **Mobile board + back navigation (0.24.0)** — three pieces:
  1. `state/overlays.tsx` + `lib/backstack.ts`: every dialog/sheet/popover/lightbox calls **`useBackDismiss(onClose)`** while open. ## Conventions & gotchas

- **No horizontal scroll / mobile**: the board grid uses `repeat(3, minmax(0, 1fr))` (plain `1fr` columns refuse to shrink below a long unbreakable token and blow out the page width); `.column` has `min-width: 0`; card title/preview use `overflow-wrap: anywhere`; `html, body { overflow-x: hidden }` is a final guard. Under 640px the topbar collapses to icon-only tabs (`.tab-label` hidden, brand logo only); the `.tabs` pill additionally SCROLLS horizontally (hidden scrollbar, `flex: 1 1 auto; min-width: 0`) so brand + theme/settings icons always stay on-screen — the shortcuts button is hidden there (`.hide-mobile`), the `.topbar-spacer` collapses, and the `.select-bar` wraps.
- **Dialog scroll**: `DetailSheet` (`.sheet--detail`) and `Composer` (`.sheet--composer`) both clip the sheet (`overflow: hidden`) and scroll only their inner wrapper (`.detail-scroll` / `.composer-scroll`, `flex: 1 1 auto; min-height: 0; overflow-y: auto`) while the header and action footer stay fixed (`.sheet--X > * { flex: none }`). Composer additionally pins its fields' height (`.composer-scroll > * { flex-shrink: 0 }`) so the area scrolls instead of squishing. MergeDialog still uses the plain `.sheet` (whole-dialog scroll). **When editing** a prompt the Composer scrim does **not** close on an outside click (`onClick={isEdit ? undefined : onClose}`) so an accidental backdrop click can't discard edits — close via ✕/Abbrechen/Esc; a new-prompt Composer still closes on click-out (its draft autosaves anyway).
- **Status transitions**: entering `running`/`done` the first time stamps `ran_at` server-side (in both `PATCH /prompts/{id}` and `/prompts/reorder`). Reorder runs in one transaction. **Done goes on top**: a PATCH to `done` uses `_top_sort_order` (min-1) instead of appending; the Board also forces a cross-column drag into done to index 0 (`dragOrigin` ref in `onDragEnd`). A successfully finished run step moves its source prompt to done-top, a failed one to failed (`runs.step_result`).
- **Board mirrors runs** (`runs._prompts_to_running`/`_release_unfinished_prompts`): `create_run` moves all source prompts into Running (append order = step order, `ran_at` stamped, blocked skipped); when a run ends without executing all steps — cancel of a queued run, run result failed/canceled (stop-on-error), or `reap_stale` — prompts of steps not in `RUN_TERMINAL` that still sit in Running return to queued. Frontend: `useCreateRun`/`useCancelRun` invalidate the prompts query so the board updates immediately; run finish updates arrive via the RunTicker's invalidation.
- **Blocked status** (`Prompt.blocked`, migration in `db.py`): toggle left of the bookmark (`BlockedButton`, red tint), **only rendered for `queued` prompts** (`canBlock` in PromptCard/ListRow/DetailSheet, analogous to `canTest`) — blocked only makes sense in the queue. Server-side: `blocked=true` on a non-queued prompt → 400; leaving queued (also via `/prompts/reorder`) clears the flag; an idempotent data fix in `db._migrate()` clears stale flags. Blocked prompts sort to the bottom of their column — the within-column ordering is centralized in **`lib/order.ts` (`columnComparator`)**, shared by Board `group()`, ListView and `navOrder`: blocked last; in DONE additionally tested-below-untested with the tested block ordered by `ran_at` DESC (latest execution on top); otherwise drag order; display-only, `sort_order` in the DB stays untouched. Blocked cards are grayed (`.card.blocked`), not draggable (attributes/listeners omitted), and the server rejects `running`/`done` with 400 while blocked (`update_prompt` guard — applied AFTER `payload.blocked`, so unblock+move works in one PATCH). All client status changes go through `applyStatus` in App (single gate + toast); "Ausführen" is hidden for blocked prompts.
- **Moving a multi-selection (0.28.0)**: a selection travels between the columns in ONE request — `POST /prompts/move {ids, status?, before_id|after_id|top}` — and lands as a contiguous block in the order it had on the board (`app/ordering.py:insert_block` keeps `ids` order; `routers/prompts.py:_move_block` is shared by the single and the bulk endpoint, so there is one implementation of the ordering rules). Two ways in, both the same call: **dragging** any selected card takes the whole selection (`lib/dnd.ts:dragSelection` picks the travelling ids in BOARD order, unit-tested), and the **select bar's target buttons** (Queued/Running/Done, board view only) — a multi-card drag is awkward on a phone and barely possible across a collapsed mobile section. `PromptCard.draggable` is what enables dragging in select mode: only SELECTED cards drag, so a tap on an unselected one still just adds it. **Every travelling card is drawn as travelling (0.28.2)**: the overlay renders the actual cards fanned behind the grabbed one (`.drag-stack-behind`, capped at `DRAG_PREVIEW_MAX`) with a count badge, and the originals stay in their columns ghosted (`.card.carried`). **Never lift the companions out of `containers`** — that was the first implementation and it silently ate cards: a drop that registered no move (`!moved`, `!from || !to`) returns early and never put them back, so a 161-card column showed 159 until a reload. It looked exactly like prompts being merged into the dragged one. Keeping them in place means there is no state to restore on any bail-out path. **Blocked prompts are skipped, not fatal** (same rule the run engine uses): they keep their status and place, and `App.moveSelection` toasts how many stayed behind — a selection of only blocked prompts is rejected with 400.
- **Hit testing and drag bookkeeping (0.28.3)** — four defects that all produced the same report, "my move isn't saved, after a reload it's back":
  1. **Collision strategy.** `closestCorners` measures corner distance, so with columns of very different height a card dragged past the end of a SHORT column snapped to a card in the tall neighbour — a drag inside Queued silently moved the prompt to Done, 690 px from the cursor. `lib/dnd.ts:boardCollision` now decides by POINTER (`pointerWithin`, `rectIntersection` as the keyboard/outside fallback) and, when the pointer resolves to a column, picks the closest card WITHIN that column (`closestCenter` over the filtered droppables) — never outside it.
  2. **Stale rects.** dnd-kit measures droppables once at drag start; auto-scroll then put them ~109 px off, so hit testing reported droppables that were nowhere near the cursor. `measuring={{ droppable: { strategy: MeasuringStrategy.Always } }}`.
  3. **Column height.** `.board` used `align-items: start`, so a short column stopped being a drop target below its last card and drops there were discarded. Now `stretch` — every column is a full-height target. Cards are capped during drags too (`visibleCards` no longer takes `dragging`): mounting all 165 cards of a long column made it ~30 000 px tall and put that many droppables under continuous measurement.
  4. **Origin bookkeeping.** `onDragEnd` asked `findContainer(active.id)` where the card was, but `onDragOver` had already moved it into the target — so every cross-column drag looked like "same column, same index", `moved` stayed false and NOTHING was sent. Use `dragOrigin.current` (captured on drag start), never the current position.
- **Stored order == displayed order (0.28.3)**: the anchor in a move names a card the user can SEE, so the server sorts the column by `app/ordering.py:display_key` — a mirror of `lib/order.ts:columnComparator` — before inserting, and `db._repair_sort_order` renumbers along the same sequence. While the two drifted apart a drag was saved and still did nothing: a queued column stores blocked prompts inline but shows them at the bottom, so "put it before #184" landed mid-list and changed nothing on screen. **Consequence for the comparator: only stored fields may take part, and every rule must be one a drag can work within.** The `ran_at` ordering of tested done prompts was therefore dropped — it made dragging them a guaranteed no-op.
- **Drag ordering is anchored, never indexed (0.27.0)**: a drag sends `POST /prompts/{id}/move {status?, before_id|after_id|top}` — a NEIGHBOUR, not a position — and the server renumbers the whole column 1..n in one transaction (`app/ordering.py:insert_block` is the pure placement rule; `routers/prompts.py:move_prompt` / `move_bookmark`). Only the TARGET column is renumbered, so a source column keeps gaps after a cross-column move — harmless, because ordering only ever compares within one status and every write path keeps the values unique. **Why:** the old `/prompts/reorder` payload was built in the browser from the cards it could SEE, so a drag with a project filter or search active numbered a subset 1..n and overwrote the order of everything it had filtered out — production had 14 done-prompts sharing `sort_order` 1, one per project, and prioritising in a filtered queue did nothing globally. An anchor id means the same thing filtered or not. Unknown anchor (concurrent change) falls back to a column edge instead of failing the drag; `_renumber` deliberately does NOT bump `updated_at` on the neighbours (they weren't edited, and the activity log would report a burst per drag). Status side effects live once in `_apply_drag_status` (shared with `/reorder`). `db._repair_sort_order` densifies pre-existing collisions on every start (idempotent, follows the displayed order so nothing visibly jumps). The `/reorder` endpoints stay for full-column callers; the frontend no longer uses them.
- **Board column cap**: max 10 cards per column, rest behind a "+N weitere anzeigen" expander; the cap holds during drags too (see the hit-testing note above). The cap logic is `lib/board-groups.ts:visibleCards`/`capToggleLabel` and the expansion is keyed **per section** (`col:<status>` desktop, group id on mobile) — it used to be keyed per status, so expanding one mobile project group uncapped every other group in that column AND the button vanished, leaving no way back (`capToggleLabel` now returns "Weniger anzeigen" instead of null).
- **Run ticker** (`RunTicker.tsx`): floating pill (fixed bottom-left) while any run is queued/claiming/running, mounted app-wide except on the Runs tab; shares the `useRuns` query with RunsView (polling stops when nothing is active). On an active→terminal transition it invalidates the prompts query (board reflects the run's done/failed move) and toasts the outcome. **Step progress**: `RunRead` carries `steps_done`/`steps_total` (steps in a terminal state vs. all, computed in `runs._run_read`/`_run_detail`) so list views get progress without loading details — the ticker appends „· 4/5 abgeschlossen" when total > 1 (summed across active runs), the Runs tab shows a `4/5` chip (`.run-progress`) in playbook header rows.
- **Runs tab expand state** (`RunsView.tsx`): each run row is a `RunCard` that fetches/polls its own detail via `useRun(open ? id : null)`, so several can be open at once. **Active runs (queued/claiming/running) are expanded by default**; a manual toggle wins via `openOverride` (per-id `Record<string, boolean>`) — an untouched active run therefore auto-collapses when it finishes.
- **Runner concurrency**: `MAX_CONCURRENCY` in `cue-runner/.env` (semaphore in `run_forever`) — currently 3 parallel runs, each its own Claude session.
- **Title derivation**: empty title → derived from the first non-blank body line (leading `#` stripped), server-side in `_derive_title`.
- **Delete with undo**: prompt deletion (single from the detail, or bulk from the select-bar) goes through `requestDelete(ids)` in `App.tsx` — the rows are hidden immediately (`pendingDelete` filters them out of `filtered`) and the real `DELETE` only fires after a 6 s undo window; the toast's "Rückgängig" action cancels it. There is no confirm dialog for prompts (the undo is the safety net); `Confirm` is still used for **project** deletion in `ProjectsView`. Toasts support an optional `action` (`toast.show(msg, tone, { action })`). Deletions still inside the undo window when the page goes away are flushed on `pagehide` via `api.deletePromptBeacon` (`fetch` + `keepalive`, since a normal request is cancelled with the page) — otherwise closing the tab within those 6 s silently resurrected prompts that had been reported as deleted.
- **Merge**: `POST /prompts/merge {source_ids, title, body, project_id, status, tags, originals}` creates the merged prompt and deletes/archives/keeps the sources in one commit (the client composes body/order/format). Requires ≥2 owned sources.
- **Open-prompt badge on the project chips (0.26.0)**: each chip carries a counter of its **queued + running** prompts (`lib/board-groups.ts:countOpenByProject`, derived in `App` from the UNFILTERED prompt list — filtering must not zero the other badges). Zero renders nothing at all. It follows the prompts query, so optimistic status changes update it without a refetch. The badge colour comes from `currentColor`, which keeps it legible in the active chip state.
- **Project order**: `Project.sort_order` is drag-sortable in `ProjectsView` (dnd-kit, `POST /projects/reorder`, optimistic `useReorderProjects`); `list_projects` orders by it, so the filter chips in `App` follow the same order automatically. The chips themselves are also drag-sortable in place (`ProjectChips.tsx`, dnd-kit `rectSortingStrategy`; a `justDragged` ref suppresses the drop-click so finishing a drag doesn't toggle the filter). New projects append (`max(sort_order)+1`).
- **Tenant scoping**: every data router depends on `current_user_id` and filters all reads + re-checks ownership on writes (404 if a row isn't the caller's). New rows always set `user_id`. When adding endpoints, never trust a client-supplied id without an ownership check.
- **Google OAuth secrets**: `GOOGLE_CLIENT_SECRET` (+ `GOOGLE_CLIENT_ID`) live only in `/opt/cue/.env`, never committed, never sent to the browser. The frontend just links to `/api/auth/google/login` (server builds the Google URL). The Google console needs origin `https://cue.celox.io` and redirect URI `https://cue.celox.io/api/auth/google/callback`.
- **User approval (0.16.0)**: sign-in is OPEN (any Google account); data access requires `User.approved`. The check lives in `deps.current_user_id` (one PK lookup per request) → revoking locks out on the next request, no session-expiry wait; pending users get 403 + a waiting screen (App-level gate on `/auth/me`.approved), logout still works (`require_csrf` doesn't depend on the approval gate). Admin = `OWNER_EMAIL` (`/api/admin/users` list + `PATCH /api/admin/users/{id}`, self-lockout blocked); UI in Settings → Nutzerverwaltung (owner-only render via `me.is_admin`). The allowlist below now means AUTO-approval, not access denial; the OAuth callback never rejects for allowlist reasons anymore. Test users from `conftest.make_user` are created `approved=True`; migration backfilled existing users.
- **Allowlist**: `GOOGLE_ALLOWED_EMAILS` / `GOOGLE_ALLOWED_DOMAINS` (comma lists) — since 0.16.0 these AUTO-APPROVE on login (plus the owner); everyone else signs in as pending.
- **CSRF secret lives inside the signed session token** — there is no separate server-side store; the readable `cue_csrf` cookie just mirrors it for the double-submit header.
- **Security headers + CSP** are set in middleware in `main.py`; HSTS is the proxy's job. CSP allows Google Fonts + inline styles (needed for runtime dynamic-color vars). **`script-src 'self'` means no inline scripts** — the pre-paint theme snippet lived inline in `index.html` and was therefore blocked (silently, apart from a console violation) ever since the CSP landed, so light-theme users got a dark flash on every cold load. It now lives in `frontend/public/boot.js` and is loaded with `<script src="/boot.js">` (no `?v=` query — that would miss the workbox precache entry). Anything that must run before React mounts goes in that file, never inline.
- **Substring search escapes LIKE wildcards** (`app/search.py`): `%` and `_` in a user's term are escaped and the query passes `escape=LIKE_ESCAPE`. Without it `?q=%` matched every row and `snake_case` matched `snakeXcase` — visible in the Tags search field. Every new LIKE goes through `contains_pattern()`.
- **Lint**: `frontend/eslint.config.js` (flat config, `eslint-plugin-react-hooks`), run via `pnpm lint` and as the first step of the root `npm test`. Ratchet: **errors block, warnings are a reviewed backlog** — `react-hooks/refs`, `set-state-in-effect`, `exhaustive-deps` and `no-useless-assignment` currently fire on patterns that were audited and found correct (latest-callback refs, effects syncing a server value into state, deliberately narrow dep arrays), so they are warnings; `rules-of-hooks` stays an error. Don't silence a warning by rewriting working code — check it first, then either fix it or leave it warning.
- **JSX + German quotes**: a straight `"` inside a `"..."` JSX attribute terminates it — use `{'…„…"…'}` (a JS string expression) for German-quoted attribute text.
- **tsconfig**: `tsconfig.node.json` is a composite referenced project and must NOT set `noEmit` (breaks `tsc -b`).
- **Project badge menu (detail sheet)**: the project badge in `DetailSheet` (a `.badge-btn`; prompts without a project get a neutral "Kein Projekt" badge) opens a `.proj-menu` popover with two modes — **Verschieben** (`PATCH /prompts/{id}` via `onMoveProject`) and **Kopieren** (`POST /prompts/{id}/duplicate {project_id}` via `useDuplicatePrompt`/`onCopyToProject`). The duplicate endpoint clones title/body/tags, always lands as **queued** in the target project, and duplicates attachment files on disk (`clone_attachment_file` in `attachments.py` — file-path logic stays in that module because its module-level `_settings` is the single source for the attachments dir; calling `get_settings()` elsewhere diverges under the test fixture's cache-clearing). Menu closes on outside click; Escape closes only the menu (capture-phase keydown listener stops propagation so the sheet stays open).
- **In-place duplicate (0.20.0)**: the ⧉ button on board cards and list rows (`onDuplicate` → `useDuplicateInPlace`) calls the same endpoint with `{in_place: true}` — full copy where it is: same project AND status (not forced queued), tags, blocked flag, bookmark (appended `bookmark_order`), cloned screenshots; title gets an incrementing counter via `_dup_title` (`Titel` → `Titel (2)` → `Titel (3)`, an existing trailing `(n)` is bumped, not nested). The copy takes the source's `sort_order`, so the higher id tie-break (`columnComparator` falls back sort_order → id) slots it directly below the original — no shifting of other rows. `tested`/`ran_at` are deliberately not inherited (done/running copies get a fresh `ran_at`); `project_id` in the payload is ignored in this mode.
- **Copy interactions**: every prompt is one-click copyable (mini copy button on cards/list rows — styled `.copy-btn`, filled primary like the detail's big copy button; plus the big button in the detail) and **double-click** on a board card or list row copies it. A single click opens the detail, so a 200 ms timer in `PromptCard`/`ListView`'s `ListRow` discriminates click-vs-double-click (double click cancels the pending open — no detail flash).
- **Double-click to edit**: double-clicking the content wrapper in `DetailSheet` (rendered preview or raw `<pre>` — the `contentRef` div; attachments/meta sit outside it) calls `onEdit` and opens the edit composer; double-clicking the composer's own Markdown preview flips `preview` off (the `[preview]` focus effect then focuses the textarea). Trade-off: word-selection via double-click is gone in these areas — select by drag or `Cmd/Ctrl+A`.
- **Composer save shortcut**: `Cmd/Ctrl+Enter` **and `Cmd/Ctrl+S`** save from anywhere in the dialog — a **capture-phase window** keydown listener (calls through a render-refreshed `handleSaveKeyRef`) plus a bubble-phase backup handler on the sheet. The two coordinate via a **WeakSet of handled events, NOT via `defaultPrevented`**: the old `!e.defaultPrevented` guard meant any earlier listener that preventDefaults the combo (e.g. a browser extension's capture listener) silently disabled saving entirely — that was the "Cmd+Enter does nothing" bug. `Cmd/Ctrl+S` is the muscle-memory fallback for setups where something outside the page swallows Cmd+Enter (preventDefault suppresses the browser save dialog). An **empty body no longer no-ops silently** (error toast "Prompt-Text fehlt" + focus back to the textarea), and a `savingRef` in-flight guard prevents double-creates from rapid repeats (button routes through the same `triggerSave`). Background: an element-bound handler alone missed the combo whenever focus sat on `<body>` (e.g. after clicking the preview).
- **Scoped select-all in dialogs**: `DetailSheet`/`Composer`-preview install a `window` keydown listener so `Cmd/Ctrl+A` selects **only** the prompt content (`Range.selectNodeContents` on a ref'd wrapper), not the whole page behind the scrim; `Cmd/Ctrl+C` then copies just that. In the detail, a bare `Cmd/Ctrl+C` with no active selection copies the full prompt. The composer **edit** textarea keeps native select-all (the listener only attaches in preview). The global shortcut handler in `App.tsx` early-returns on any meta/ctrl/alt combo, so these never collide.
- **Last-used project**: creating a prompt stores its project in `localStorage` (`cue-last-project`); the next new prompt preselects it (validated against the live project list; an active project filter still wins via `defaultProjectId`).
- **Brand icon**: `frontend/public/favicon.svg` is the single source (celox-family style: `#0d1117` tile, `#30363d` hairline border, lavender `#a78bfa` queue-lines + bolt motif). The PWA PNGs (192/512/maskable — maskable = motif at 64 % in the safe zone) are rendered FROM it via the headless-chromium pipeline; topbar + login embed it as `<img src="/favicon.svg">` (`.logo-img`), and the OG card mirrors the motif. Changing the icon = edit the SVG, re-render PNGs + og.png + screenshots, bump the favicon `?v=` in index.html.
- **Landing/Login page**: signed-out visitors see the login card first (fast access wins — the audience is small and admin-approved), then a `LandingFeatures` tour in `Login.tsx` with demo screenshots under `frontend/public/landing/` (fictional content, regenerate by seeding a scratch DB and screenshotting; excluded from the workbox precache via `globIgnores` so the PWA cache stays lean). The README screenshots under `docs/screenshots/` come from the same pipeline (fictional demo content — board/detail/runs/snippets/list/mobile/light) and should be regenerated after larger UI changes.
- **Clickable brand**: the cue logo+wordmark in the topbar (`.brand-btn`) reloads the page (hover primary tint, press scale).
- **Header project label**: the board view shows the active project filter next to the brand (`TopBar` `projectLabel` prop, `.brand-project` chip, remounted `motion.span` per label so the spring replays; hidden <760px).
- **Save-shortcut hint is platform-aware**: `lib/platform.ts` (`IS_MAC`/`detectMac`, unit-tested) — composer + snippet editor render ⌘↵ on macOS, `Strg ↵` elsewhere. The keydown handlers accept `metaKey || ctrlKey` on EVERY platform on purpose (fallback if a system-wide macOS shortcut swallows Cmd+Enter); don't "fix" them to be exclusive.
- **kbd-in-button legibility**: `.btn kbd` derives its chip background/border from `currentColor` (`color-mix`) so the `⌘↵` hint stays readable on filled/tonal/danger surfaces instead of dark-on-dark.
- **No native browser dialogs** — `window.prompt/confirm/alert` are banned. Use `Confirm` (message + danger action) or `InputDialog` (`components/InputDialog.tsx`: MD3 text input, autofocus+select, Enter=OK/Esc=Cancel, `validate` callback for inline errors like duplicate names).
- **Recharts custom content inherits the chart's `stroke`**: the Treemap's `stroke` prop outlined the tile LABELS with the card colour and made them unreadable. Custom `content` must set `stroke="none"` on its `<text>` and draw the tile border on the `<rect>` itself (`var(--md-*)` does resolve in SVG presentation attributes, so the border follows the theme).
- **Never write `Prompt.tags` directly** — it is derived state. Go through `TagService.set_for_prompt()`, or the cache and the links drift apart.
- **New overlays MUST call `useBackDismiss(onClose)`** — that is the single registration point for back-gesture *and* Escape handling. Never add another branch to a manual Escape chain.
- **Optimization is owner-only and runner-bound**: without a running `cue-runner` jobs just sit in `queued` (the reaper only touches `running` ones). The runner needs no extra config — `CUE_OPTIMIZE=0` disables its worker loop.
- **Statistics ranges** persist in `localStorage` (`cue-stats-range`, the whole `{range, from, to}` object). The KI section is hidden entirely when the tenant has no runs (`ai: null`), and `session_minutes_median` is a **median** on purpose — one CLI session left open for days would wreck the mean.
- **Conventional Commits**. Persist app state lives entirely in the SQLite file (`/data/cue.db` in the container volume).

Update: `rsync ./ root@69.62.121.168:/opt/cue/` then `ssh ... 'cd /opt/cue && docker compose up -d --build'`.
